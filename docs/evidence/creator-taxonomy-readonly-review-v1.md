# 博主分类、公开发现与个人偏好：只读研究 V1

日期：2026-10-23（UTC+8）

状态：研究完成，方案待确认；应用未修改。

用户已确认的目标：**访客发现＋管理员整理**。用户另已明确，“保留和喜欢是我个人的爱好，未来匿名用户不应该看到这个分类”；本轮研究如何实现这一边界，不直接修改应用。

## 1. 结论摘要

建议增加独立的“创作方向”，以 **Cosplay、写真、日常自拍** 作为三个首版候选方向，允许一位博主同时选择多个方向，也允许暂不分类。R15/R18 继续单独表示内容分级。三类是否充分覆盖用户想区分的内容，仍需少量自选样例确认。

用户举出的名称确实能帮助区分内容，但含义并不在同一层：Cos 和写真侧重内容，抖音和维密圈是平台名称，“抖音风”是风格描述，“福利姬／网黄”又混合了内容尺度、经营方式和对人的称呼。把这些放进同一个互斥下拉框，会很快遇到“一人到底选哪一类”的问题。

研究建议分为三项，优先级如下：

1. **先隔离站主偏好。** 当前“喜欢／保留”在公开图库中仍可读取和筛选；未来应只供管理员使用。仅隐藏按钮或只删响应字段都不足够。
2. **再增加公开创作方向。** 类别关联规范博主身份，用于发现和整理；具体作品的类别由 Work 单独描述，不能自动继承为全部作品的事实。
3. **按需要增加作品维度和个人关注。** 原作、角色、主题均为可选；博主关注属于当前访客，与站主偏好、现有作品收藏分别管理。

以上是建议。用户确认了研究用途，尚未确认类别名称、作品分级规则、关注存储方案，也未授权本轮实施。

当前旧链接中的“待分类”实际对应博主分级为空。增加创作方向后，应分别称“未设置分级”和“未归类”，避免用户误以为选择 R18 就完成了内容分类。[C2][C4]

### 3.1 需要先处理的站主偏好读取边界

**代码事实：** public 模式允许匿名读取图库。博主列表、博主详情，以及作品列表内嵌的 creator 对象，均包含站主 `preference`。图库首页“全部／喜欢／保留”按钮没有管理员条件；服务端也接受 `preference=liked|kept`，在分页前过滤并返回结果和总数。[C2][C3][C4][C5]

**运行观察：** 2026-10-23 17:19（UTC+8），使用不携带 Cookie、不复用登录会话的请求，取得以下结果。未保存博主姓名、ID、个人偏好清单或总量。

| GET 路径 | 观察结果 |
| --- | --- |
| `/api/auth/status` | HTTP 200；匿名，认证已开启，public 模式 |
| `/api/cos-gallery/creators?page=1&limit=1` | HTTP 200；有样本，包含 `preference` 字段 |
| `/api/cos-gallery/creators?page=1&limit=1&preference=liked` | HTTP 200；有样本，返回偏好与所请求筛选值一致 |
| `/api/health` | HTTP 200；构建身份如第 2 节 |

这确认了匿名读取路径的问题；没有证据表明匿名能修改站主偏好。偏好保存已有管理权限限制；默认图库排序按最近作品时间、名称和稳定 key，并非按站主偏好排序。[C2][C3]

**研究建议：**

- 公开读取使用明确的字段白名单，列表、详情、内嵌 creator 均去掉站主偏好；管理接口保留。
- 非管理员请求中的 `preference` 必须在筛选前处理。兼容旧链接时，建议统一忽略这一管理条件，并清除前端 URL 状态；同一公开查询加不加该参数，结果、总数和排序都应一致。若选择明确拒绝，也需先处理旧链接，避免整页报错。
- 前端隐藏非管理员偏好控件；查看者 viewer 也不应获得站主偏好，不能只针对 anonymous。
- 返回导航会保留 preference 参数，需兼顾旧链接和历史状态。已有角色变化时的阅读缓存失效机制应保留并验证，不凭空断言它已失效。[C8]

本轮仅记录问题及整改边界，未实施以上行为。

## 4. 建议拆开的维度

以下全部为研究建议，不是已实现的数据结构。

| 维度 | 回答什么问题 | 建议对象 | 展示对象 |
| --- | --- | --- | --- |
| 创作方向 | 这个博主主要创作哪些内容？ | 规范博主，多选 | 访客与管理员 |
| 作品类别 | 这一套具体是什么？ | Work，单独确认，可多选 | 访客与管理员 |
| 内容分级 | 作品适合怎样的浏览范围？ | 保留现有分级；未来明确 Work 判定与博主汇总关系 | 按公开访问规则显示 |
| 媒体形态 | 图片、视频还是混合？ | Work 内实际可见媒体 | 访客与管理员 |
| 风格／主题／原作／角色 | 想继续找怎样的作品？ | 主要属于 Work，均可空 | 经确认的公开字段 |
| 平台与来源 | 在哪里发布、转载或收集到？ | 博主账号关系＋Work 来源证据 | 公开身份与内部来源分开 |
| 站主偏好 | 我喜欢谁、决定保留谁？ | 站主与博主的关系；当前全局字段可继续供管理使用 | 管理员 |
| 我的关注 | 当前访客想持续查看谁？ | 当前访客与规范博主的关系 | 该访客本人 |

R15/R18 在这里描述内容，不能推断人物真实年龄，也不能把类别标签当成访问控制。pixiv 的官方帮助明确区分普通 R18 标签和实际浏览限制；这是分开设计这两类功能的参考，并非要求照搬其评级体系。[S1]

### 4.1 三个首版方向的操作定义

| 候选方向 | 归类依据 | 不应自动推断 |
| --- | --- | --- |
| Cosplay | 有明确的角色扮演或 Cosplay 创作内容 | 不必已知原作／角色名；不能据此判断 R15/R18 |
| 写真 | 以人物形象、服装、场景等为主题的成套拍摄，便于查找通常所说的人物写真 | 不能把所有照片都自动归写真，也不能把写真等同于成人内容 |
| 日常自拍 | 以自拍、生活化表达或日常记录为主要内容 | 不等于只来自抖音，不等于低画质，也不限于视频 |

“写真”与 Cosplay 可以重叠；这些是帮助发现的方向，不是严格互斥的职业。管理员按已确认的代表内容多选，不需要给每人指定唯一主类。卡片显示少量方向，详情显示完整归类；没有资料的博主保留未归类状态。

“短视频”先放在媒体／时长维度，不另设“短视频博主”去吞掉所有含视频的 Cos 和写真。若用户以后确实大量按舞蹈、表演等内容查找，再考虑新增方向或主题，首版不预建大词库。

### 4.2 用户提到的称呼如何落位

| 原称呼 | 推荐处理 |
| --- | --- |
| Cos 博主 | 创作方向：Cosplay |
| 写真博主 | 创作方向：写真；可与 Cosplay 同时选中 |
| 抖音风自拍／网图 | 确认内容后选择日常自拍或写真；“抖音风”可作可选风格词。网图说明传播形态，不能证明作者或首发来源 |
| 抖音、维密圈 | 分别记录为已核实的平台／来源信息；本轮没有验证两者隶属、同步或账号对应关系，不把括号视为等号 |
| 福利姬、网黄 | 暂不设为互斥公开人物类别；如有整理价值，可保留管理员录入的原词及来源备注，避免自动公开或扩展为身份别名 |

对最后一项，这些区别可能分别由以下维度表达：成套拍摄归“写真”，生活化自拍归“日常自拍”，内容尺度用分级，性感风格可作可选作品风格，订阅／会员来源放在来源信息。是否覆盖用户的检索需求仍待样例确认。不能从收费、平台名称或昵称反推 R18，也不能把所有 R18 博主统一称为“网黄”。

如果用户确实需要“成人向创作”作为公开发现入口，应先明确它是否只是 R18 的另一个显示名称，还是独立创作方向，以及何种证据可归类。首版不重复建立两个意思相同、维护却可能矛盾的字段。

## 5. 博主与作品各自如何使用分类

### 5.1 博主层先落地，避免扩大首版

最小方案是管理员给规范博主添加多选创作方向，图库增加“找博主”的方向筛选。选择“Cosplay 博主”表示找到有这类创作的博主；进入人物页后仍可浏览其不同类型作品。

这一步可以独立使用，不必先给已有所有 Work 打标，也不需要搬动文件、拆分同一人物、重新入库或重建来源身份。未归类对象正常收录，全部列表仍可找到；未归类不自动授予公开访问权限，也不在本研究中改变现有公开范围。

### 5.2 作品发现再细化

如果要筛出“Cosplay 的作品”，就需要 Work 自己的类别，不能只筛出 Cosplay 博主再把该博主所有写真、自拍一起称为 Cos 作品。

- 原作可以不知道，角色可以不知道；一套有多个角色时允许多个关联，确认同名角色要结合原作。
- 主题／风格可从少量有检索需求的词开始，例如棚拍、户外、日常感；不为了完整而要求每套都填。
- 同一 Work 的两个 LocalWork 共用作品事实；副本只保留文件、路径与可用性等信息。
- 类别不能作为判重规则：同博主、同角色、同主题仍可能是不同作品。
- 合作作品涉及其他人物时保留既有 Work 身份合同；本轮分类研究不顺带改写单／多作者模型。

博主方向允许管理员维护；将来可根据已分类作品生成“建议方向”供确认。建议不能静默覆盖人工分类，删除最后一套某类别作品也不应自动抹掉对博主的人工描述。

### 5.3 筛选与计数要讲清口径

1. 同一维度多选默认“任一匹配”，不同维度“同时满足”。例如“Cosplay 或写真”＋“含视频”。
2. “找博主”结果数按规范博主去重；“找作品”按可见的独立 Work 去重。不能把本地副本数、外站套数混为作品数。
3. 作品组合筛选必须由**同一件作品**同时满足条件。某博主有一套 R15 Cos 和一套 R18 写真，不代表存在 R18 Cos。
4. 博主创作方向＋博主现有分级，只表示两项博主属性；在作品分级机制明确前，不能将它宣传为作品级筛选。
5. 计数、封面和推荐仅使用当前访问者可见的作品；回收、不可用或未来未发布内容不应借计数透露给访客。
6. 切换条件回第一页；进入详情再返回，保留公开筛选、排序、分页和位置。访客旧链接中的管理偏好应按第 3.1 节处理。

## 6. 个人偏好与“关注博主”

当前 `liked/kept` 的含义可以继续保留为站主整理工具，没必要为了访客发现删除已有个人数据。管理员在博主库使用“站主偏好”，公开图库使用“创作方向”。

“关注”若要实现，建议定义为：**把规范博主加入当前访问者的“我的关注”，方便下次查看其作品。** 默认不同时意味着通知、订阅收费、作品点赞或内容发布授权。

| 阶段候选 | 行为与成本 |
| --- | --- |
| 匿名本机／首版公开访问 | 可参照现有本地收藏方式，在浏览器保存规范 creatorId；明确显示“关注仅保存在此浏览器”。清除站点数据或更换浏览器后不会自动同步 |
| 需要跨设备时 | 建立真实访客账户及每用户关注关系，再设计同步、迁移、删除等行为；当前共享 viewer 身份不能冒充个人账户 |
| 更新提醒 | 与关注另行设计。本轮不引入邮件、推送、自动采集或定时通知 |

本地关注只影响当前浏览器，不生成公开关注量；博主删除、合并或不再公开时，需要处理已保存的 ID，不泄露不可见资料。若以后支持登录，本地关注迁移应由用户确认，不能无声合并。

YouTube 官方帮助把订阅与登录用户、订阅信息流相联系，并单独说明通知设置。这支持“关注是个人关系、提醒另有范围”的产品参考；CosGallery 无需因此立刻引入账号系统。[S2]

## 7. 访客与管理员看到什么

| 场景 | 建议呈现 |
| --- | --- |
| 访客找博主 | 名称／别名搜索＋创作方向＋语义明确的现有分级；偏好按钮不可见 |
| 访客看博主 | 规范名、已确认的公开别名和方向、可见作品；若后续获准实现，提供个人“关注” |
| 访客找作品 | 作品类型与媒体形态；原作、角色、主题可展开。作品元数据不足时不伪造精确结果 |
| 管理员整理 | 创作方向多选、未归类过滤、站主偏好、分级、启停和来源分别呈现；批量操作前明确选中范围 |
| 不知道该怎么归类 | 允许为空、记录待确认；无需依靠“其他”大类吞掉所有未知 |

类别宜有稳定标识和可修改显示名，避免改中文名称就断掉旧链接。第一版使用少量受控词表；新增、停用、合并类别时保留已有关系或明确迁移，不自动重分配真实博主。

平台身份、公开个人主页与内部收集来源需要分别对待。下载链接、会员链接或带令牌地址不因增加“来源筛选”就自动公开。未来如果把预览图发布到 R2，仍应只导出获准公开的媒体和元数据；本研究不设计上传、部署或对象存储权限。

## 8. 用合成例子验证方案

以下为未来实现时的产品验收例子，本轮没有执行功能测试或改动真实分类。

| 合成场景 | 应有结果 |
| --- | --- |
| 博主甲既有角色 Cos，也有普通写真 | 可选两个方向；不会创建两个博主 |
| 甲的一套作品是日常自拍 | 不因作者有 Cosplay 方向就自动获得 Cos 或角色标签 |
| 甲有 R15 Cos 和 R18 写真 | 精确的“R18 Cos 作品”查询不能把任意一套误匹配 |
| 一套写真来自抖音，另有转载来源 | 类型仍可为写真；首发与收集来源不混写，不推断两个账号就是同一人 |
| 一个 Work 有两个本地副本 | 作品数为 1，分类随 Work；回收／恢复仍按原有范围操作 |
| 管理员喜欢甲，访客 A 关注乙 | A 只看自己的关注；匿名响应和偏好参数都不能暴露管理员的选择 |
| 刚入库的博主没有方向或角色信息 | 正常入库与后续整理，不批量推成 R15、不自动获得公开资格 |
| 访客沿旧链接携带 `preference=liked` | 按既定兼容规则处理，不能改变公开结果为站主喜欢的子集 |
| 从管理员切到匿名再返回图库 | 清除管理条件，公开响应无私有字段，历史缓存不带出偏好 |

## 9. 推荐推进顺序与待确认项

研究 PR 可保留以下三个独立阶段，不自动转为实施任务：

1. **公开／管理读取边界。** 修正站主偏好字段、筛选、旧链接和控件；验证 anonymous、viewer、admin 三种角色。无需等待完整分类体系。
2. **博主创作方向。** 先确认三个首版候选方向，支持多选、允许为空；复用规范博主身份，支持公开发现和管理员整理。既有数据不按 R18、平台或目录名自动批量归类。
3. **按实际需要深化。** 作品级类别、原作／角色／主题；个人关注单独确定本地保存还是账户同步。不要将它们绑成首版上线前的全部前置条件。

实施前需要确认的产品选择：

- “日常自拍”是否符合用户要收录的抖音风内容；是否有大量舞蹈／表演内容需要另一个方向。可用少量用户自选样例讨论，无需扫描全库。
- “福利姬／网黄”带来的检索需求，能否由方向＋分级＋风格＋平台覆盖；如不够，再定义有明确边界的公开名称。
- 现有博主分级如何与 Work／Post 分级衔接，未知分级及成人内容的公开访问规则是什么。本轮不把分级过滤误称为完整年龄限制。
- 是否本阶段就需要访客关注；若需要，能否接受仅此浏览器保存。关注与跨设备账户是不同工作量。
