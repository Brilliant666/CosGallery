# 博主分类、公开发现与个人偏好：只读研究 V1

日期：2026-10-23（UTC+8）

状态：研究完成；用户已确认本阶段分类范围与选择方式，应用尚未修改。

用户已确认的目标：**访客发现＋管理员整理**。本阶段只给博主增加 **Cosplay／写真／自拍／福利姬** 四种标签，用于图库模块的博主筛选；一人允许多标签，下拉框每次选择一个标签。“喜欢／保留”仅供管理员整理。

## 1. 结论摘要

用户在研究之后已明确选择四个图库博主子分类：**Cosplay、写真、自拍、福利姬**。管理员为规范博主分配一个或多个标签，图库通过单选下拉框筛选博主，R15/R18 保留为独立筛选。

本次确认取代初稿的三个候选方向：将“日常自拍”显示名收敛为“自拍”，加入用户明确选择的“福利姬”。四者作为可重叠的整理标签使用，无需强行选定唯一职业，也不按分级或平台自动推断人物属性。

已确认的边界：

1. **只筛博主。** 四个子分类的结果是博主卡片，不是作品或媒体列表；分类能力不扩展到其他模块。
2. **标签和分级独立。** 一位博主可有多个标签；图库下拉框每次选一个。标签条件与现有 R15/R18 条件同时生效。
3. **站主偏好只供管理员。** 当前匿名读取及筛选偏好的问题仍需后续同时处理页面、响应字段和查询参数。
4. **控制范围。** 本阶段不新建作品标签、原作／角色／主题或平台来源能力；访客关注也不作为本阶段实施项。

本次只更新研究文档和 PR 范围。分类数据、应用代码和运行实例均未修改；已确认产品方案不等于功能已实现。

### 3.1 需要先处理的站主偏好读取边界

**代码事实：** public 模式允许匿名读取图库。博主列表、博主详情，以及作品列表内嵌的 creator 对象，均包含站主 `preference`。图库首页“全部／喜欢／保留”按钮没有管理员条件；服务端也接受 `preference=liked|kept`，在分页前过滤并返回结果和总数。[C2][C3][C4][C5]

**运行观察：** 2026-10-23 17:19（UTC+8），使用不携带 Cookie、不复用登录会话的请求，取得以下结果。未保存博主姓名、ID、个人偏好清单或总量。

| GET 路径 | 观察结果 |
| --- | --- |
| `/api/auth/status` | HTTP 200；匿名，认证已开启，public 模式 |
| `/api/cos-gallery/creators?page=1&limit=1` | HTTP 200；有样本，包含 `preference` 字段 |
| `/api/cos-gallery/creators?page=1&limit=1&preference=liked` | HTTP 200；有样本，返回偏好与所请求筛选值一致 |
| `/api/health` | HTTP 200；构建身份如第 2 节 |

这确认了匿名读取路径的问题；没有证据表明匿名能修改站主偏好。偏好保存已有管理权限限制；默认图库排序按最近作品时间、名称和稳定 key，并非按站主偏好排序。[C2][C3]

**研究建议：**

- 公开读取使用明确的字段白名单，列表、详情、内嵌 creator 均去掉站主偏好；管理接口保留。
- 非管理员请求中的 `preference` 必须在筛选前处理。兼容旧链接时，建议统一忽略这一管理条件，并清除前端 URL 状态；同一公开查询加不加该参数，结果、总数和排序都应一致。若选择明确拒绝，也需先处理旧链接，避免整页报错。
- 前端隐藏非管理员偏好控件；查看者 viewer 也不应获得站主偏好，不能只针对 anonymous。
- 返回导航会保留 preference 参数，需兼顾旧链接和历史状态。已有角色变化时的阅读缓存失效机制应保留并验证，不凭空断言它已失效。[C8]

本轮仅记录问题及整改边界，未实施以上行为。

| 标签对象 | 规范博主，关联稳定 creatorId |
| 标签数量 | 一位博主允许多个标签 |

四种标签由管理员明确设置。“福利姬”采用用户确认的显示名，不另换成初稿建议的其他名称；不根据 R18、抖音、维密圈、文件夹名或昵称自动批量赋值。既有平台来源记录继续原有职责，本阶段不新增相关实体、筛选或界面。

未设置标签仍可正常收录。建议默认展示在“全部”中；不把归类作为入库前置条件，不把现有博主自动归入某一类。

## 5. 下拉筛选如何工作

建议下拉框名称为“博主分类”，选项为：

- 全部
- Cosplay
- 写真
- 自拍
- 福利姬

“全部”用于清除标签条件，不是第五种标签。管理员编辑的是多选标签；访客筛选是单选条件，两者行为明确分开。

举例：博主甲有“Cosplay＋写真”两个标签。选择 Cosplay 时能找到甲，选择写真时也能找到甲；选择全部时甲只出现一次。

标签、现有分级、名称搜索同时生效。例如选择“写真”与“R18”，返回具有写真标签、且现有博主分级为 R18 的博主。**这是博主属性筛选，不能据此声称其每套作品都是 R18 写真。** 本阶段不改变 Work／Post 分级机制。

筛选在分页前完成，总数按规范博主去重。切换条件回到第一页；打开博主后再返回，保留标签、分级、搜索与分页状态。现有排序及可见范围继续适用，无匹配时显示“没有符合当前条件的博主”，允许清除筛选。

## 6. 管理员编辑与偏好隔离

建议在图库的博主卡片或详情提供仅管理员可用的“编辑分类”入口，以四个复选项多选保存。具体入口位置属于实现细节；不因此给博主库、资源目录或短片新增分类筛选。

标签随规范博主身份保存，同一人的多个本地目录共用标签；不拆博主、不移动文件、不写入作品或副本分类。既有别名只承担身份搜索，不保存分类词。

“喜欢／保留”继续保留现有个人数据和管理用途：

- 管理员可继续查看、筛选和修改站主偏好。
- anonymous 与非管理员 viewer 均不可通过图库控件、列表、详情、内嵌 creator 或筛选参数读取站主偏好。
- 旧链接中的管理偏好参数需按第 3.1 节处理；只隐藏前端按钮不够。
- 本阶段不新增访客“关注博主”，也不把站主喜欢直接改名为访客关注。

## 7. 本阶段不包含的内容

初稿中有关 Work 分类、原作／角色／主题、平台与来源、个人关注及 R2 的建议，不进入本阶段。用户明确暂不需要作品标签和平台来源新能力。

本次范围不要求整理全库、补齐标签或重新入库，也不改变公开发布范围、原媒体、预览策略、回收语义或现有数据库记录。分类标签只表达管理员的内容整理，不负责判重、身份合并或访问授权。

R15/R18 与类别仍需分别处理。pixiv 官方说明中，普通 R18 标签和实际浏览限制是不同设置；这里仅用来说明分类标签不能代替访问控制，不扩大为本轮新的分级或年龄限制工程。[S1]
