# 应用恢复点

恢复点保存**完整应用数据库及配套配置材料**，不是原媒体备份，也不是撤销某次入库的按钮。主数据仍在现有数据库和图库中，不迁移 `DATA_ROOT`，不建立第二套作品库。

## 保存什么

| 纳入 | 不纳入 |
| --- | --- |
| SQLite 全部表、索引和迁移记录，包括目录派生表及计划历史 | TB 级图库原件、等待区与处理中媒体 |
| 实际加载的 `.env`、明确指定或唯一匹配的运行 `.run` 配置 | 全部 `.idea`、`node_modules`、`dist` |
| `DATA_ROOT/private` 中已有且恢复需要的密钥 | 图片派生缓存、`.mocks` 历史发布材料 |
| 完成时间、来源实例、代码/schema 版本、文件清单和验证结果 | 浏览器插件存储、Cookie、未保存的页面输入 |

本地保存的解压密码需要数据库密文与 `local-ingest-archive-password.key` 配套。缺失必要密钥、密钥错误或无法解密会阻止发布恢复点，不生成新 key 冒充原 key。配置完整性表示本实例所需配置已由备份材料与对应代码版本的默认值覆盖，**不要求使用 PyCharm 或存在 `.run`**；“数据库完整性通过”与“配置材料足够恢复”分别判断。

元信息和网页不返回密码、key 内容或整个进程环境。备份目录本身含敏感材料，应作为私有恢复材料保管；不要上传 Git、公开网盘或私人清单到 PR。

## 位置与配置

| 环境变量 | 默认值 | 说明 |
| --- | --- | --- |
| `BACKUP_ROOT` | 当前应用仓库根目录的 `data_backup` | 相对值以代码确定的仓库根解析，不依赖启动 shell 的 cwd。 |
| `BACKUP_AUTO_ENABLED` | `false` | 日常自动恢复点开关；未开启时仍可手动创建及执行必要的操作前保护。 |
| `BACKUP_INTERVAL_HOURS` | `24` | 至少 24 小时；启动时检查一次，运行中每 15 分钟检查到期，下次启动可补当前恢复点，不逐日补历史。 |
| `BACKUP_RETAIN_DAILY` | `7` | 最近的日常恢复点保留目标。 |
| `BACKUP_RETAIN_WEEKLY` | `4` | 另外保留最近各周代表恢复点；同一份可同时满足日常和周保留目标。 |
| `APP_ENV_FILE` | 仓库根 `.env` | 实际加载并收集的环境配置文件；隔离运行明确指定自己的文件。 |
| `APP_RUN_CONFIG_FILE` | 未指定 | 明确指定实际运行配置文件，并核对其格式和有效配置。未指定时仅收集能解释必要进程注入、且与实例匹配的唯一 `.run.xml`；不因目录中只有一份文件就认定它实际生效。 |

### 配置完整性如何判断

- **不适用**：`.env` 与当前代码默认值已覆盖实例配置，且没有明确使用 IDE 配置时，缺少 `.run` 不产生告警。没有实际加载 `.env`、只使用代码默认值的实例也不要求伪造文件。
- **已确认的运行配置**：明确指定且校验匹配的 `.run` 会被收集。未明确指定时，只有唯一可靠候选能解释文件/默认值未覆盖的实际进程设置，才自动收集它。
- **来源未确认**：多个匹配候选不擅自选一份，也不复制全部配置来宣称完整。仍有必要进程设置未覆盖时，报告相关配置名称与来源未确认说明；如果文件与默认值已经覆盖，则不因目录里有多份无关 `.run` 告警。
- **实际缺失或不一致**：显式 `APP_RUN_CONFIG_FILE` 指向缺失、无效或不匹配的文件时，保留对应提示；显式 `APP_ENV_FILE` 缺失同样是恢复缺口。不能将用户明确指定但缺失的文件改称“不适用”。
- **未覆盖的进程注入**：按应用现有配置 schema、默认值及实际模式判断必要设置，元信息只保留名称和需另行恢复的要求，不保存明文值或整个进程环境。`.env` 和已确认 `.run` 的定位指令本身不重复算成缺口；恢复时使用收集的材料，并核对该实例的实际路径。

新判定只用于新建恢复点。旧恢复点的 `configuration.complete`、缺口说明及其他元信息保持创建时的历史记录，不批量改写；设置页明确标示这一点。若最新历史记录仍含旧判定，可创建新恢复点取得当前判断，不需要修改旧材料。

解压密码按**实际备份快照**判断：快照已有本地密码或明确停用记录时，Worker 验证数据库决定后（密文须使用所复制密钥验证），不再把被覆盖的 `LOCAL_INGEST_ARCHIVE_PASSWORD` 列为恢复缺口；没有数据库决定时，未保存的环境密码仍是缺口。此判断不依赖启动 Worker 前读取的提示，不改动用于检测配置/密钥变化的原始清单，也不抹去其他真实缺口；必要密钥缺失、错误或无法解密仍阻止成功发布。

开发 worktree、测试和隔离预览必须显式配置自己的 `BACKUP_ROOT`。复制正式配置到测试时尤其要检查目标，不能让测试清理正式恢复材料，也不能把正式数据库长期备份到临时 worktree。

目标不能与数据库、配置/密钥、图库、等待区、处理中目录、可服务的缓存或前端静态目录重叠。仓库内目标仅允许 `data_backup` 及其子目录；其他自定义位置必须在仓库外，避免敏感材料进入 Git 或构建上下文。新恢复点使用独立名称，不覆盖主库、旧备份或其他文件。`data_backup` 被 Git 和容器构建忽略；HTTP 与 Vite 也有独立读取保护，不能把 `.gitignore` 当作访问控制。

## 网页操作

管理员进入 **设置 → 扫描与图库 → 备份与恢复点**：

1. 查看实际位置、最近成功记录、配置缺口和自动策略。
2. 点击“立即创建恢复点”，后台完成一致性复制及验证。
3. 可离开设置页，返回后重新读取状态。创建中自动查看进度；读取失败时可手动刷新，不自动重发创建。
4. 只有发布成功的完整记录进入成功历史。失败保留上一份成功恢复点，未完成临时目录不是可恢复点。

列表 GET、打开设置和普通首页读取都不会创建恢复点。网页不能指定任意源路径、下载 `.env`/key 或覆盖正在运行的主库。原管理权限、同源变更保护及只读演示限制继续生效。

## 共用维护入口与操作前保护

仓库内维护命令使用相同服务和固定配置目标：

```sh
pnpm --filter @foldergram/server recovery-point status
pnpm --filter @foldergram/server recovery-point create
```

配套 production 构建可使用：

```sh
node server/dist/scripts/recovery-point.js status
node server/dist/scripts/recovery-point.js create
```

推荐 Node.js 24；CI 使用的当前 Node.js 22 也覆盖该功能。恢复点使用的 [SQLite online backup API](https://nodejs.org/download/release/latest-jod/docs/api/sqlite.html) 从 Node.js 22.16.0 起提供，不应使用更早的 22.x 执行恢复点创建。

这些入口只查看或创建恢复点，不导入会自动迁移主库、扫描图库或启动 Worker 的业务初始化入口，也不执行恢复。

已存在数据库真正需要 schema 升级或已支持的结构修复时，在**第一处修改前**创建恢复点，包括 baseline/不完整迁移标记修复。新空库不伪造“升级前业务数据”，无迁移/修复的日常启动不重复备份。用户明确执行“重建图库索引”时，先成功生成恢复点再进入重建；不是持有数据库写事务或同一维护锁后递归等待备份。

必需的恢复点失败，只阻止该次升级/重建，保留原输入和确认范围。普通读取不因可选自动备份失败而停用。批量入库、永久删除等其他维护操作本轮不逐文件自动加备份；维护人员可在**整批操作之前**使用手动入口，避免把每张图片处理变成一次全库备份。

## 一致性、失败与保留

生成顺序：独立临时目标 → SQLite 一致性备份 → 收集配置/key → 只读验证副本 → 完成元信息 → 发布成功目录。验证包括 `integrity_check`、`foreign_key_check`、来源 schema/迁移版本及业务表；不会为验证旧快照先迁移它。数据库复制、校验和文件哈希在后台执行，不在首页请求线程一次性读取整个数据库为 Buffer。

配置和 key 在生成期间变化时拒绝把不匹配组合标记为成功。并发网页点击、维护 CLI 和自动任务使用同一互斥机制；不会互相覆盖。进程中断留下的临时结果继续保持未完成，不因重启变成成功记录。

自动策略默认关闭；开启后只在服务运行期间检查，不安装 Windows 计划任务或独立守护进程。成功创建新恢复点后，才整理本机制可识别、同实例的日常记录，保留日常与周代表的并集。**手动、维护及重要操作前恢复点首版不自动删除**。已有手工备份和 `.mocks` 发布材料不参与清理。

## 隔离恢复步骤

本版本不提供“一键覆盖主库”。恢复需要明确操作和停写窗口：

1. 核对所选记录为成功恢复点、文件清单、schema 版本和兼容应用代码。恢复旧 schema 不等于允许执行 down；不要擅自用新版初始化入口打开它。
2. 停止可能写入的服务、目录 Worker、CLI、插件和自动队列。先另外保留当前数据库、日志、配置/key及故障现场，不能先覆盖再诊断。
3. 将所选恢复点复制到独立恢复验证目录，使用只读 SQLite 核对完整性、外键、schema，以及必要业务关系。校验配置/key文件与清单，不输出敏感内容。
4. 核对规范博主与别名、Work/LocalWork、主副本、来源对应、固定排序决定、满足关系和原计划历史。不能仅凭两条 PRAGMA 通过宣布业务恢复完整。
5. 对照备份完成之后的入库、文件移动、回收、来源资料和人工决定。**旧数据库不包含后来的决定，恢复点也没有原媒体**；旧路径可能已经不存在，新移动位置可能仍有真实文件。
6. 先在隔离实例使用独立数据库、媒体样本、缓存、private 和备份根验证，不连接真实图库执行扫描。确认后才制定实际切换及必要的索引对齐方案。

不自动扫描全库、不重放所有 planned/failed 任务、不重新执行已完成的历史计划。扫描可以重新发现可读文件，但不能重建丢失的人工对应、版本接受、来源满足和排序决定；这些需保留并按证据处理。旧计划未完成也不等于作品当前仍未入库。

同一磁盘的恢复点主要应对应用误操作与数据库问题，不能防磁盘整体损坏。原件与异机/离线备份需另行安排；本机制不宣称覆盖它们。
